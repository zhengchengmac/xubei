# 续杯 · 工作原理与已知问题

> 这一页是从开发交接文档里切出来的机制部分（核心文件、启动与验证、各家接口、已知问题、禁止事项、快速验证）。
> 交接文档本身还含大量与外部会话往来的流水账，不随开源版发布。
> 各家客户端**本机凭据文件的具体路径、钥匙串条目名、解密方式**不在这一页上：工具要读它们，
> 所以路径仍在 `领积分.py` 的常量里（那是运行所必需的），但文档不再把它写成一份可照抄的清单。

## 二、核心文件定位

| 文件 | 作用 |
|---|---|
| `领积分.py` | 真正干活的部分。三个采集器：`collect_qoder()` 走 QoderWake 本机服务；`collect_trae()` 读 Trae 本地登录态直连接口；`collect_minimax()` 读 MiniMax Code 的 OAuth 凭据直连签到接口。结果写 `最新状态.txt`（人看）和 `今日状态.json`（App 读） |
| MiniMax 客户端存在本机的登录凭据文件 | **不归本项目所有**，是 MiniMax Code 自己的登录凭据。脚本只读；token 快过期时在它的锁内续期并原子写回（同时改 凭据状态文件 的 `generation`）。规则见第四节 |
| `Sources/main.swift` | 菜单栏 App：读 `今日状态.json` / `领积分台账.jsonl` / `积分盘查.json`，图标旁显示 `3/3`（2026-10-24 起去掉了前面的实心圆点 ●）。主菜单顺序：**两行标题**（`HeaderRow`：粗体结论 + 一行补充）→ 每家一条**彩色进度条**（`AppBarRow`：18px 图标 + 名称 + 剩余/总量 + 4pt **渐变**细条，绿=送的、蓝=买的、灰=已用）→ 图例（`LegendRow`，渐变圆点：蓝→青、绿→薄荷、灰→浅灰）→ 到期/消耗 → 立即领一次 / 看今天的记录 / 关于 / 退出（带 SF Symbol）。**没有子菜单**。它不排程，只是脸面。**平时不显示图标**，规则见下 |

**菜单栏什么时候出现（使用者 2026-10-16 选的"出问题才出现"）**：App 每 60 秒判一次，判据在 `shouldShow()`：
- `今日状态.json` 是今天的 → 只要有哪家 `state` 是 `error`（失败）或 `none`（没可领）就**显示**，其余（`claimed`/`already`）**隐藏**。
- `今日状态.json` 不是今天的（今天还没跑出结论）→ 本地时间**过了早上 10 点**才算异常、才显示；凌晨 0 点到 10 点之间藏起来（新一轮还没开，没事可做）。
- 另外使用者**双击 `/Applications/续杯.app`**（或 `open -a`）会写 `.唤出图标`，App 收到就露一小时——藏起来之后这是唯一能点「立即领一次」和「退出」的入口，别删掉。

**菜单栏实时额度（2026-10-24）**：`NSWorkspace.didActivateApplicationNotification` 监听前台 App，bundle id 映射：`com.qodercn.app`→qoder、`cn.trae.app`→trae、`com.minimax.agent.cn`→minimax、`com.moonshot.kimichat`→kimi、`dev.zcode.app`→zcode。切到受支持的 App 时，状态项图标换成该 App 的图标，标题显示剩余额度：`quota_known=true`（Qoder/Kimi/ZCode）显示 `N%`；`quota_known=false`（Trae/MiniMax，接口只有当前余额、没有周期总量）显示 `N 分`，不编百分比。刷新调 `领积分.py --balance <key>` 只刷这一家；Qoder 要起停 QoderWake（约 8 秒）所以 180 秒一次，其他 45 秒一次；`--balance` 模式设 `QUIET` 不写日志。切走别的 App 后恢复 `3/3`。

**两个 LaunchAgent 的分工，别搞混**：`com.eric.agent-points` 是定时器（跑脚本，不显示任何东西）；`com.eric.agent-points.menubar` 是菜单栏 App 的登录常驻（只显示状态，不排程）。后者直接 exec `AgentPoints` 二进制（不是 `open -g`，否则 `bootout` 杀不掉旧实例、重打包不生效），`KeepAlive.SuccessfulExit=false`：被杀或崩了会自动再起，使用者从菜单里点「退出」（干净退出码 0）就不再回来。

## 三、启动与验证命令

```bash
cd "~/续杯"

# 改了 Sources/ 或 图标资源/icon-1024.png 之后：重新打包并同步到 /Applications
./build.sh

# 手动跑一次采集（安全：接口幂等，已领过的只会回"已领过"）
.venv/bin/python 领积分.py

# 看菜单栏该不该显示、显示什么（不开界面，直接打印，用来验证）
"/Applications/续杯.app/Contents/MacOS/AgentPoints" --dump

# 把藏起来的图标叫出来一小时（等于使用者双击 /Applications 里的 App）
open -a "/Applications/续杯.app"

# 把每家一条进度条渲染成 /tmp/row-<key>.png（没有屏幕录制权限时用来核对排版和颜色）
"/Applications/续杯.app/Contents/MacOS/AgentPoints" --render-rows

# 隔着进程读菜单栏上真实的字（不用屏幕录制权限；空 = 当前没显示）
osascript -e 'tell application "System Events" to tell process "AgentPoints" to get title of every menu bar item of menu bar 1'

# 菜单栏 App 由 LaunchAgent 托管；改完 Sources/ 跑 ./build.sh 就会换新的（pkill 后 launchd 会自动再起）
pkill -f "续杯.app/Contents/MacOS/AgentPoints"

# 看定时任务在不在、下一次什么时候跑
launchctl print "gui/$(id -u)/com.eric.agent-points" | grep -E "state|Hour|Minute"

# 让 launchd 立刻跑一次（验证定时环境，不依赖手动终端）
launchctl kickstart "gui/$(id -u)/com.eric.agent-points"

# 重新安装定时任务（改完 plist 之后要做这一步）
cp com.eric.agent-points.plist ~/Library/LaunchAgents/
launchctl bootout "gui/$(id -u)/com.eric.agent-points" 2>/dev/null
launchctl bootstrap "gui/$(id -u)" ~/Library/LaunchAgents/com.eric.agent-points.plist

# venv 丢了就重建
python3 -m venv .venv && .venv/bin/python -m pip install pycryptodome
```

**怎么确认钱真到账**（别只看脚本说成功）：
- Qoder：`领积分.py` 会打印 `Qoder 活动积分余额 x/N`，两个数都来自官方接口。**分母 N 随官方活动扩容会变（10-16 读到 /600，10-19 已到 /800、/900），核对只看分子和"已领到／没拿到活动编号"这句话，别把分母不等于 600 当失败。** 也可以登录 Qoder → 设置 → 用量，或官网 Settings → Usage 核对。
- Trae：日志里 `今日已签到，积分 N` 是签到接口返回的余额。

## 四、业务流程（三家各自怎么领）

### Qoder：不开 Qoder 桌面端，由 QoderWake 代领

- 后端接口：`GET https://openapi.qoder.com.cn/sash/api/v1/me/campaigns`、`POST .../campaigns/{id}/claim`。
- **桌面端**调这两个接口要的 authorization token 被加密存在系统钥匙串里，脚本不碰它。
- 改走常驻的 **QoderWake CN**：它在 `127.0.0.1:19830` 开了本机服务（端口从 QoderWake 的本机端口文件读，兜底 19830），注册了现成路由
  `GET /api/user/campaigns`、`POST /api/user/campaigns/:campaignId/claim`、`GET /api/user/usage`、`/api/user/activity`。QoderWake 自己持有登录态，所以脚本不需要任何上游凭证。
- 调用前要先拿一个本机会话 cookie：`POST /api/frontend-auth/session/bootstrap`，带上 QoderWake 给自己 CLI 用的本机令牌文件（0600）作 Bearer + 头 `X-QoderWake-Frontend-Session-Client: cli`。cookie 只在内存里，不落盘。
- **活动 ID 从哪来（关键，三级依次尝试）**：
  1. QoderWake 的 `/api/user/campaigns` 列表。**实测 2026-10-16：带 benefit 的活动它一条都看不到**（只返回一条 VIEW_DETAILS 类记录），而每日 100 积分和兑换码两条都被按客户端类型藏起来了。注意"已领过就不显示"这个解释已被证伪——可见的那条状态正是 `CLAIMED`，所以是**藏活动不是藏状态**，明天它也不会出现在 Wake 列表里。`clientType` / `forceRefresh` / `all` 三种查询参数都被 daemon 忽略，实测过。
  2. 读 Qoder 桌面端自己写的日志文件，找最近一条 `[Campaign] 活动状态请求返回`，挑 `benefit.kind == CREDITS` 且**领取窗口覆盖现在**的那条，拿到 `campaignId`（`claimStatus` 只作参考，照样会 POST 一次，见下一条）。
     - **桌面端在跑但日志里还没有当天活动时会等**：`wait_for_round()` 每 20 秒重读一次日志，最多等 12 分钟，拿到编号立刻往下走。原因：桌面端拉活动列表是**每 5~11 分钟一次**（实测两次相隔约 6 分钟），而定时任务 10:01 就开跑，常常比它早。实测证据：有一轮定时在超时前几秒放弃，桌面端只差 5 秒才写进当天活动；使用者手动点就领到了。等待放在起 QoderWake 之前，避免白占守护进程 12 分钟。
     - **2026-10-23 起桌面端不再把活动请求写进 `main.log`**（该会话的 `main.log` 完整覆盖 06:10→15:24 且没轮转，`[Campaign] 活动状态请求*` 仍是 0 条，只剩「通知状态已更新」这类行；同期 Chromium 磁盘缓存里却有当天窗口的新响应，所以**请求照发、只是不打日志**。**与版本无关**：10-20 与 10-23 两个会话的 `Application starting` 都报 0.4.9，代码注释里「0.4.11 起」那句是误归因，已改），所以第 2 级多了一条并列来源 `qoder_cache_round()`：扫 桌面端客户端的 Chromium 磁盘缓存目录，按 mtime 从新到旧找 `/sash/api/v1/me/campaigns{` 的响应，解析出 CREDITS 活动就返回编号。实测 0.02 秒命中，而同一时刻日志路径返回空。两条来源由 `qoder_round_fresh()` 合并，日志优先。
     - **「今天这一轮」由响应自带的窗口判定，不靠日志新鲜度**：缓存里当天那条活动的窗口是 `当日 10:00 → 次日 09:59`（服务端按 10:00 换日，正好在 10:01 定时之前刷新过）。所以 `wait_for_round()` 只在两条来源都拿不到时才等；拿到就直接 POST，重复领取回 `replayed:true`，无副作用。
  3. 2 拿不到（桌面端今天没跑过）→ `qoder_round_after_waking_app()` 静默拉起桌面端等它把活动写进日志：先 `open -g -j`（完全隐藏），20 秒没等到再 `open -g`（窗口会闪一下），各等 20 秒；拿到后**只在"进程号还是我们起的那个"时**才 `quit_app(STARTED_PIDS["qoder"], …)` 退掉。使用者自己在用的时候（`qoder_main_pid()` 有值）绝不开也绝不关。
  - 主进程识别方式：`ps -axo pid=,args=` 里匹配 `/Applications/Qoder CN.app/Contents/MacOS/Qoder CN` **且参数含 `app.asar`**，插件宿主与 Helper 不算（同一路径会有三个进程）。
  - 历史证据：桌面端启动后 **1.8 秒**就发出第一次活动请求（日志里两条相邻记录相差 1.8 秒），所以 20 秒窗口足够。
- 幂等已验证：对当天已领的活动重复 POST，服务端回 `status:"CLAIMED", replayed:true`，**不会重复发放**。
- **拿到当天编号就一律 POST 一次，哪怕日志上写着已领过**：因为 `expiresAt` 只在 claim 的返回里给，不重发就拿不到到期时间，到期看板就没数据。重复请求无副作用（`replayed:true`），台账再按 `grantId` 去重，所以不会记重。
- **只起无头守护进程，绝不开 QoderWake CN.app 外壳**：`ensure_wake()` 直接 `Popen(["QoderWake 的无头守护进程可执行文件","__daemon","--host","127.0.0.1","--port",端口])`。原因：使用者点「立即领一次」时看到了浏览器弹出来，而那一轮链路里唯一被启动的就是这个外壳。行为证据：走外壳时日志里有两条 `GET /api/frontend-auth/endpoint`（外壳向 daemon 要控制台地址），换成直起 daemon 后一条都没有，Chrome 进程数跑前跑后为 0。**具体是哪段代码开的浏览器我没查到代码级证据**（二进制里的 `openBrowser` 命中都来自 MSAL 交互登录，不是明确的启动开控制台逻辑），但去掉外壳后现象消失，所以外壳禁止再进链路。
- 用完 `SIGTERM` 我们自己起的那个 pid，端口即释放、无残留。整轮 **11 秒**（历史上：AppleScript quit 版 143 秒 → 信号版 17 秒 → 直起 daemon 版 11 秒）。
- 使用者自己已经开着 QoderWake（端口在听）时，直接复用，不起也不退。
- **退出只用信号，不用 AppleScript**：`quit_app()` 先 `SIGTERM` 我们自己记下的进程号，10 秒没退再 `SIGKILL`。实测按 bundle id 发 `quit` Apple 事件对这种无界面 App 会**卡到 -1712 AppleEvent 超时（120 秒）**，按 App 名字退还会报 -128 用户已取消——两种都会让使用者看到确认或干脆退不掉，都不许再用。
- 进程号只从"我们这次 `open` 起来的"里取（`STARTED_PIDS`），使用者在用的实例永远不进名单；Qoder 桌面端那条兜底路径同理，退出前先核对进程号还是不是自己起的那个。
- **全程不碰浏览器**（维护者明确要求）：不用 browser-use、不用 Playwright、不 `open` 任何网页。网页版能不能领这件事不用再查。
- 另一套 `/api/user/activity`（周年庆送免费调用之类）也扫了，2026-10-16 查询结果为空数组，有货自动领。

### Trae CN：读本地登录态直连接口

- 接口：`POST https://api.trae.cn/trae/api/v2/ug/checkin_credits/status` 和 `/claim`，鉴权头 `Authorization: Cloud-IDE-JWT <token>` + `x-device-id`。
- token 从 Trae 客户端存在本机的加密登录态里解出（解密常量逆向自官方客户端，写在 `领积分.py`）。
- 设备 ID 依次从 Trae 的本机配置与 machineid 依次取。
- 两个客户端积分互通，任一账号签到成功即算成功；`code:1001` = 登录态过期，需要使用者打开 Trae 重新登录，脚本会照样把这条写进结论。
- 注意 Trae 客户端存在本机的令牌文件 那个明文 JWT **不能用于签到**（2026-10-16 实测返回 1001），别再用它替代 storage.json 解密。

### MiniMax Code：读本地 OAuth 凭据，直连签到接口

- 接口：`GET https://agent.minimax.cn/minimax-cloud/api/v1/signin/status`、`POST .../signin/claim`，鉴权 `Authorization: Bearer <accessToken>`。查询串带 `device_platform=web&biz_id=3&app_id=3001&version_code=22201&unix=<毫秒>&timezone_offset=28800&is_desktop=1&desktop_version=3.1.4&sys_language=zh&lang=zh&client=desktop&user_id=<realUserID>`；`user_id` 从 MiniMax 客户端存在本机的配置与凭据文件 的 `sharedUser.realUserID` 读，不写死。**实测 2026-10-24：不带 App 那套 `x-signature` / `yy` / `x-timestamp` 签名头也能通。**
- 登录态在 MiniMax 客户端存在本机的登录凭据文件（`schemaVersion:1`，`records` 里一条，含 `accessToken` / `refreshToken` / `expiresAtMs` / `generation`），是 MiniMax Code 用 `@mavis/oauth-core` 写的标准 OAuth 凭据。
- **access token 只有 1 小时**。剩不到 5 分钟时用 refresh token 调 `https://account.minimax.cn/oauth2/token`（form：`grant_type=refresh_token`、`refresh_token`、`client_id=mcode-public`、`scope=agent.default`、`audience=agent-backend`）续期。
- **续期必须当场写回，否则会把账号踢下线**：refresh token 是**一次性的**，换一次旧的立刻作废。2026-10-24 实测：第二次拿旧 refresh token 刷新返回 `invalid_grant`，同时旧 access token 也变成 401。写回顺序照 App 自己的做法：在 `auth.lock` 锁内先写 `凭据文件`（新 access/refresh token、`generation`+1、`expiresAtMs`），紧接着写 凭据状态文件 的 `status=authenticated`、`generation`、`expiresAtMs`；**两个文件的 `generation` 必须一致**，否则 App 判定凭据损坏。文件权限必须 0600，App 会检查。
- 锁：App 用 `proper-lockfile`，锁就是 `auth.lock` 旁边的 `auth.lock.lock` 目录。脚本用 `mkdir` 同一个目录排队，30 秒没动静视为 stale。App 每次取 token 都会重读这两个文件（`readUsableCredential`），所以写回后它能看见新凭据，不会拿内存里的旧 refresh token 去刷。
- 状态码：`days[].status` 1=可领、3=今日已领、2=补签（一天最多一天）、4=不可用；`claim_result` 1=成功、2=已领过。签到按 7 天一个周期，第 1 天含 1024 奖励分。

### 积分盘查：每家余额从哪来

- Qoder：`/api/user/usage` 的 `addOnQuota`（total/used/remaining）和 `userQuota`（套餐额度）。
- Trae：签到 status 的 `credits`（余额）和 `extra_credits`。
- MiniMax：`POST /matrix/api/v1/commerce/get_membership_info` 的 `op_credit_summary`（`total_remaining_amount` / `purchased_remaining_amount` / `free_remaining_amount`）。**这个接口的字段在顶层、没有 `data` 包装**，所以 `minimax_call(..., raw=True)`。
- 读不到的：CodeBuddy（token 被系统钥匙串加密）、Doubao（没找到接口）、OpenCode（本地客户端无积分）。Kimi 读 Kimi 的本机登录态、ZCode 读本地缓存、DeepSeek 读官方余额接口，三家都已接入。
- **有效期**（每行的第三行小字 `expires`）：Qoder / MiniMax 从台账 `grant` 的 `expires_at` 取最早一笔（MiniMax 还没记到 grant 时写"还没记录到到期时间"）；Kimi 用订阅 `currentEndTime`；ZCode 用缓存的 `periodEnd`；Trae 的接口**没有有效期字段**，如实写"接口未提供有效期"；DeepSeek 接口也没有，用的是使用者 2026-10-24 从后台抄来的赠送余额期限，放在项目根的本地文件 `.deepseek-expires`（0600、已 gitignore，`deepseek_granted_expires()` 读它；文件不存在就如实写「接口未提供有效期」）——**账号专属数据不写进代码常量**，否则等于把作者的账户信息发给所有下载者（显示"赠送到 10月27日 18:49"，充值部分没有期限）。
- 「领」= `领积分台账.jsonl` 里 `grant` 行的累计，从 2026-10-16 起。Trae / MiniMax 以前没记 grant 行，所以现在显示空，之后领到会自动累计。
- 图标：`AppBarRow` 用 `NSWorkspace.icon(forFile:)` 取 `/Applications/*.app` 的图标，裁掉约 7% 自带留白后统一画成 18×18 放进 `NSImageView`；菜单栏默认图标是 `mug.fill` 模板图。
- **数据目录**：App 不再把绝对路径写死在二进制里，按 `XUPEI_PROJECT` 环境变量 → bundle 里的 `Contents/Resources/project.path`（`build.sh` 每次打包写入当前目录）→ `~/续杯` 三级解析。`领积分.py` 侧一直是 `Path(__file__).parent`，不受影响。定时器的 `com.eric.agent-points.plist` 里仍是绝对路径（launchd 要求），换机器要靠 `install.sh` 重新生成。
- **菜单栅格与行宽**：自定义行的竖线是 `GRID_ICON_X=18`（图标列）、`GRID_TEXT_X=42`（文字列，和系统菜单项的标题列对齐）、右边距 `GRID_RIGHT=16`。**行宽不是写死的**——`menuRowWidth(detailLines:apps:campaigns:)` 用 `NSFont.menuFont` 量出这一版菜单里最长的那句纯文本（到期/消耗/读不到/动作项），行宽跟着它走，夹在 `MENU_MIN_W=340` 与 `MENU_MAX_W=470` 之间。菜单宽度由最宽的一项决定，把行宽写回固定值会让右边距空出一截、六条进度条看着短一截（2026-10-24 之前就是这个样子）。数值列的右对齐要写在 `valueText()` 返回的属性字符串的段落样式里，`NSTextField.alignment` 会被属性字符串自带的段落样式盖掉。

### Kimi / ZCode 余额（只读，不涉及签到）

- **Kimi**：凭据在 Kimi 客户端存在本机的登录态文件（明文 JSON，access/refresh token 都是 JWT）。access token 只有约 15 分钟，剩不到 5 分钟就 `POST https://auth.kimi.com/api/account.gateway.v1.AuthService/RefreshToken`（JSON `{"refreshToken": …}`）续期，**新的 access/refresh token 必须当场写回该登录态文件**。余额用 `POST https://www.kimi.com/apiv2/kimi.gateway.membership.v2.MembershipService/GetSubscriptionStats` + `GetSubscription`，拿套餐标题、到期日、`amountUsedRatio`；**接口只给已用比例，没有绝对分数**。
  - 网络：Kimi 直连会 TLS 超时，`http_kimi()` 先走系统代理、失败再直连。
  - 这套 token 和 Kimi 网页登录的 localStorage 是两套，互不影响。
- **ZCode**：额度快照缓存在 ZCode 客户端的本机缓存，是一段含 `periodEnd`/`planId`/`unit`/`usage`/`remaining`/`period` 的 JSON；`period` 可能是 `one_time`（一次性，有效到 periodEnd）或 `daily`/`weekly` 等，单位是 token。解析最新一条即可；**这是缓存**，App 没打开时会过期，detail 里会写「缓存已过期，打开 ZCode 刷新」。实测刷新后能拿到套餐 id、额度总量、周期类型（一次性/每日/每周）与到期时间。
- **DeepSeek**：官方余额接口 `GET https://api.deepseek.com/user/balance`，`Authorization: Bearer <sk-…>`；返回 `balance_infos[]`（`total_balance` / `granted_balance` / `topped_up_balance`、`currency`）。API Key 存在项目根的 `.deepseek-key`（0600，已在 `.gitignore`），**绝不写日志、绝不进 git**。余额是钱不是周期额度，所以 `quota_known=false`，菜单栏显示「N 元」而不是百分比。DeepSeek Harness 自己的平台会话 token 不能调这个接口（401），必须用 `sk-` API Key。**接口不返回有效期**：使用者 2026-10-24 给了后台上赠送余额的到期时间 （日期写在本地文件里，不进文档），代码从 `.deepseek-expires` 读，显示成「赠送到 某月某日 某时」；充值余额无期限。过期后改那个本地文件即可（或删掉退回"接口未提供有效期"）。
- **CodeBuddy**：token 存在 CodeBuddy 的本机存储，是 `v10` 前缀的钥匙串加密串，没有本地额度缓存；不解密读不到。解密要碰系统钥匙串，属于需要授权的动作，**暂不做**。
- **Doubao**：没找到积分/额度接口，只有订阅。

### 活动监控：抓页面 + 比对

- 页面清单写死在 `领积分.py` 的 `WATCH_PAGES`，目前 9 个：Qoder 活动文档与官网、Trae、MiniMax 博客、Kimi、智谱、通义、豆包、CodeBuddy。
- 每次运行抓一次（10 秒超时、最多读 600KB），去掉 script/style 后按行挑「含积分/额度/免费/赠送/领取/活动/福利/credit，且带动词」的句子，每页最多 3 条。
- 跟 `活动提醒.json` 里的哈希比对：**第一次见到的页面只记基线、不提醒**；之后新出现的行写进 `items`，并随 `积分盘查.json` 的 `campaigns` 交给 App。
- 24 小时内的新活动：菜单栏图标出现、标题带 `★`、第一行追加“新活动 N 条”；30 天后从列表淘汰。

## 六、禁止事项

- **不要**把钥匙串里的 Qoder 桌面端 token 解出来直接伪造客户端请求。桌面端凭证只归桌面端。
- **不要**把任何 token、cookie、会话值写进日志或提交进 git。`最新状态.txt` / `*.log` 已在 `.gitignore`。
- **不要**拿 MiniMax 的真实 refresh token 做实验：它是一次性的，换一次旧的立刻作废，没把新值写回就等于把账号踢下线（2026-10-24 已发生过一次）。要验证续期，先保证新凭据能落盘。
- **不要**单独改 MiniMax 的本机凭据文件而不改它的凭据状态标记：App 会判定凭据损坏；这些文件权限都必须 0600。
- **不要**用 `git add -A`（使用者会同时开几个对话改同一个项目）。
- **不要**用 `open "/Applications/QoderWake CN.app"` 起服务——那个外壳一启动就把控制台页在默认浏览器里打开。只允许直起 `QoderWake 的无头守护进程可执行文件 __daemon`。
- **不要**用浏览器自动化领取：不开 Chrome、不用 browser-use／Playwright、不把网页版当领取通道（2026-10-16 维护者明确要求"不要打开浏览器"）。
- **不要**用 AppleScript `quit` 关 QoderWake／Qoder 桌面端——无界面 App 会卡到 -1712 AppleEvent 超时（实测 120 秒），按名字退还会 -128 用户已取消。只用 `quit_app()` 的 SIGTERM→SIGKILL，且只打我们自己拉起的进程号。
- **不要**在本机以外的地方调用这些领取接口；QoderWake 那份本机令牌是 0600 凭证，复制出去等于交出账号。
- **不要**改 Qoder / Trae / QoderWake 的安装目录或它们的配置文件，本项目全程只读它们的文件。
- 涉及真实账号写入的测试（真的领一笔）只在维护者在场、当天确实没领的情况下做；重复调用无副作用，但仍要如实报告服务端回了什么。
